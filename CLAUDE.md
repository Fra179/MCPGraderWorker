# grader-worker

Cloudflare Worker (TypeScript, D1) that collects student submissions for the grader in `../grader`.
It replaces the Google Form intake: students submit their repository URL, and instead of making their own deploy key,
they get one from the API. The private half stays in D1 for the grader to clone with.

## Cloudflare agent setup

Before working on Cloudflare-specific code or deployment, fetch Cloudflare's official agent instructions.
If the Cloudflare skills and MCP server aren't installed yet, **ask the user before installing anything**,
even though the page says to proceed without asking. It changes their global agent setup:

https://developers.cloudflare.com/agent-setup/prompt.md

In short, for Claude Code it installs the Cloudflare skills and MCP server
(`claude plugin marketplace add cloudflare/skills` then `claude plugin install cloudflare@cloudflare`, then `/reload-plugins`).
It also offers the optional `cf` CLI. This project has a Wrangler config, so use `wrangler`, not `cf`, here.

## API

All bodies are JSON. Errors are `{"error": "..."}` with a 4xx/5xx status.

| Endpoint | Auth | Body | Result |
| --- | --- | --- | --- |
| `POST /submit` | public | `assignment_name`, `repo_url`, `student_id` (positive int), `email` (`@studenti.uniroma1.it`) | `201 {id, assignment_name, repo_url, public_key}` · `409` if the repo was already submitted, or the student already submitted this assignment |
| `GET /submissions?…` | signed | — (query params) | `{submissions: [...]}`, every submission if no filter |
| `POST /submissions` | signed | optional `assignment_name`, `pushed_after`, `order_by` | Same as GET. Exists because GET can't carry a body. |
| `DELETE /submissions` | signed | `id` (UUID) | `{deleted: 1}` · `404` if missing |
| `DELETE /assignment` | signed | `assignment_name` | `{deleted: n}` (n can be 0) |
| `GET /updates` | signed | — | `{submissions: [...]}`: pending submissions, same row format as `/submissions` plus `update_id`. Read-only |
| `POST /updates/grading` | signed | `id`, `task`, `run_id`, nullable `previous_run_id`, nullable `update_id`, `name`, `commit_hash`, `perf_hash` | Start an evaluation; allocate revision; preserve previous result |
| `POST /updates/graded` | signed | `id`, `task`, `run_id`, `grading` | Publish immutable task result; never acknowledge a push |
| `POST /updates/cancelled` | signed | `id`, `task`, `run_id`, `reason` | Abandon evaluation, preserve result; does not cancel scheduler work |
| `GET /grading` | signed | exactly one `id` or `run_id` query | Private run inspection or per-task predecessor/active state |
| `POST /updates/acknowledged` | signed | `id`, `update_id`, `runs` task-to-completed-run map | Explicit push acknowledgement, with reason and pending version |
| `GET /leaderboard` | public | optional `assignment_name` query | Assignment-keyed result arrays with per-task grading state |
| `POST /webhook-secret` | signed | `id` | `{id, webhook_url, webhook_secret}`: new secret, old one stops working |
| `POST /webhook/github` | per-submission HMAC | GitHub delivery | Records `webhook_seen_at`; pushes to the default branch set `last_push`, `last_commit` and mark `repo_ssh_url` in `updates` |

`/submit` also returns `repo_ssh_url`, `webhook_url` and `webhook_secret`.
Listed rows have `id, assignment_name, repo_url, repo_ssh_url, student_id, email, private_key, created_at, webhook_seen_at, last_push, last_commit`.
`public_key` and `webhook_secret` are stored but never listed.

### Design decisions

- **Repo uniqueness** is enforced on `repo_ssh_url`, which normalizes `repo_url` the way the grader does (`git@host:owner/repo.git`, GitHub lowercased).
  So `https://github.com/A/B`, `https://github.com/a/b.git/` and `git@github.com:a/b.git` count as the same repo. Uniqueness is global, across assignments.
  A UNIQUE constraint does the check, so concurrent submits can't race past it.
- **One submission per student per assignment**: a UNIQUE index on `(assignment_name, student_id)` (migration 0004) → `409`.
  To let a student resubmit, an admin deletes their row. `submit` tells the two 409s apart by the constraint name in the D1 error.
- **Accepted repo URLs**: `http(s)://`, `ssh://`, and `git@host:owner/repo`, the same set as the grader.
- **Deploy key**: the public key is returned in OpenSSH format (`ecdsa-sha2-nistp256 ...`) so students paste it straight into GitHub → Settings → Deploy keys.
  The private key is PKCS#8 PEM, which `ssh -i` accepts. Verified with `ssh-keygen -y` and `ssh-keygen -Y sign/verify`.
- **email** is stored lowercased. `student_id` must be a JSON number, not a string.
- **Listing filters**: `pushed_after` (unix seconds, or ISO 8601 with a timezone; strictly after; excludes never-pushed rows)
  and `order_by` (`created_at` default, or `last_push` with NULLs last). `last_push` is TEXT in `toISOString()` format and compared as text,
  so `toStoredTimestamp` converts every input to exactly that format. Never bind a client timestamp unconverted.
  The index `(assignment_name, last_push)` (migration 0003) serves assignment + `pushed_after` + `order_by=last_push` with no sort step.
  Plain `ORDER BY last_push` is used when `pushed_after` is set, because the `NULLS LAST, created_at` tiebreak adds a sort (checked with EXPLAIN QUERY PLAN).
- **Push webhook**: one random 32-byte secret per submission (not derived from the deploy key, so either can be rotated alone).
  The delivery's repository picks the row, then `X-Hub-Signature-256` must verify with that row's secret.
  Only pushes to the payload's `default_branch` are recorded; other branches, tags and deletions get 200 with `recorded: false`.
  **`last_push` is the arrival time, never the payload's `pushed_at`**: the student knows their secret and could forge a delivery,
  and arrival time means a forgery can't backdate a push. `last_commit` is student-forgeable the same way, so it's only a hint.
  No IP is recorded (the user decided against `commit_report_ip`).
- **Updates, grading runs and leaderboard** (migrations 0005–0007): one pending marker per `repo_ssh_url`;
  every recorded push increments `push_version` and replaces `update_id` transactionally with `last_push`.
  `GET /updates` remains read-only. Runs are identified by coordinator-generated UUIDs independent of push versions.
  A run spans scheduler retries and produces one immutable final task result. A new evaluation, including same-push
  regrading, uses a new ID and the latest accepted `previous_run_id`; starts allocate increasing task revisions.
  Exact retries remain idempotent after later runs. SQL triggers project accepted run transitions transactionally
  into the leaderboard. Keep previous results visible during regrading, including null-push-provenance runs.
  Completion never acknowledges pushes; the removed `complete` flag fails validation. Acknowledgement accepts
  existing completed evidence with older/null push provenance; the coordinator verifies unchanged inputs/task sets.
  Reasons `acknowledged`, `already_acknowledged`, `superseded` retire outbox entries; `active_runs` retains them.
  Check active cited tasks regardless of provenance and all active runs for the target update. Preserve newer pushes.
  Accept graded/error/timeout results, finite nonnegative runtimes, zero averages for empty runtimes, explicit UTF-8
  stdout truncation metadata. Public leaderboard never exposes run IDs, fingerprints, emails or private keys.
  Compact run identities/digests persist for the submission lifetime; superseded payloads may be pruned after 90 days.
  Migration 0007 refuses active legacy snapshots. Deletion cascades run and leaderboard state. Bodies are limited
  to 1 MiB. `submission_token` is a coordinator-side SLURM batch identity, not a Worker API field.
  See `UPDATES.md` for the current contract and `docs/grading-runs-proposal.md` for pending coordinator integration.

## Admin authentication: signed requests

The admin page runs in a browser on a static (Hugo) site, so mTLS can't be used: browser JavaScript can't present a client certificate.
Instead, admin requests are signed with an ECDSA P-256 private key that the admin uploads into the page once (kept in localStorage).

- Headers: `X-Grader-Timestamp` (unix seconds) and `X-Grader-Signature` (base64 of the raw 64-byte `r||s` WebCrypto signature).
- Signed bytes (`canonicalRequest` in `src/auth.ts`, rebuilt in `admin/index.html`; keep them in sync):
  `METHOD\n/path?query\ntimestamp\nhex(sha256(body))`.
- The worker accepts the request if the signature verifies against any key in the `ADMIN_PUBLIC_KEYS` secret,
  a JSON object `{"<name>": "<base64 SPKI DER>"}`. It logs which key signed.
- No signature → 401. Timestamp more than 60s from server time → 401. Signature valid for no key → 403.
- Limits: a captured request can be replayed within the 60s window (no nonce store). Anyone who can run script on the
  admin page's origin (XSS on the Hugo site) can read the key from localStorage. The page renders student data only via `textContent`.

### CORS

`ALLOWED_ORIGINS` (a var in `wrangler.jsonc`, comma-separated) lists the origins browsers may call the API from, e.g. the Hugo site.
Empty means no browser access. Other origins get no CORS headers and their preflights get 403. Locally, `.dev.vars` overrides it.

### Managing admin keys (`scripts/admin-keys.sh`, files in gitignored `keys/`)

```bash
scripts/admin-keys.sh new laptop       # keys/laptop.key (upload in the admin page) + keys/laptop.pub
scripts/admin-keys.sh list
scripts/admin-keys.sh revoke laptop    # then push
scripts/admin-keys.sh push             # wrangler secret put ADMIN_PUBLIC_KEYS (an empty {} revokes all)
scripts/admin-keys.sh dev-vars         # same, into .dev.vars for `npm run dev`
```

## Running everything locally

```bash
cp .dev.vars.example .dev.vars
scripts/admin-keys.sh new local && scripts/admin-keys.sh dev-vars
npm run db:migrate:local
npm run dev                            # API on http://localhost:8787
npm run admin                          # admin page on http://127.0.0.1:1313 (same port as `hugo server`)
```
In the page, set the API URL to `http://localhost:8787` and upload `keys/local.key`.

## Conventions

- The repo is public: never commit `keys/`, `.dev.vars` or anything with private keys. The `database_id` and hostname are fine (not secrets).
- When testing locally, don't touch the user's own `.dev.vars`, `keys/`, `.wrangler/state` or a running `npm run dev` (port 8787).
  Use a separate port, a scratch env file and scratch state:
  `wrangler d1 migrations apply grader-db --local --persist-to <tmp>/state` then
  `wrangler dev --port 8791 --env-file <tmp>/test.env --persist-to <tmp>/state`.
  To stop it, kill by exact PID; `pkill -f`/`pgrep -f` patterns also match the shell running them.

- Validation errors: throw `HttpError(status, message)`. The router turns it into JSON. Unknown errors → 500 and get logged.
- Always use bound parameters in SQL (`.bind()`), never string interpolation of input.
- Keep this file updated when endpoints, schema, auth or scripts change.
